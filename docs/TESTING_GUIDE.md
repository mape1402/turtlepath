# TurtlePath Testing Guide

This guide documents the TurtlePath testing packages and the recommended testing paths for handlers, automations, persistence, hooks, jobs, exception handling, and event sourcing.

## Packages

### TurtlePath.Testing

Core testing package for fast unit tests and lightweight integration tests.

Use it when the test can run with TurtlePath abstractions instead of real infrastructure.

Main features:

- `TurtlePathTestHost`
- `TurtlePathTestHostBuilder`
- delegate mapper adapter
- delegate validator adapter
- in-memory TurtlePath storage reader/writer
- hook tracing
- Pelican dispatch helpers
- automation registration helpers
- exception handling helpers
- one-shot job helpers

### TurtlePath.Testing.EntityFrameworkCore

SQLite-backed integration testing package.

Use it when the test must prove actual EF Core behavior:

- DbContext model configuration
- EF storage adapters
- query translation
- save behavior
- entity configuration
- TurtlePath EF conventions
- CId conversion behavior

### TurtlePath.Testing.EventSourcing

Event stream assertion package for TurtlePath event sourcing.

Use it when a command or hook should append events and the test needs to assert the resulting stream.

## Test Levels

### Handler Unit Test

Use this when the application owns a concrete handler class and the test should focus on the handler behavior.

Recommended characteristics:

- direct handler instance
- fake in-memory storage
- delegate mapper
- delegate validator
- optional hook trace
- no real database
- no real mapper/validator provider

Example:

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .WithMap<CreateCustomerRequest, Customer>(request => new Customer
    {
        Id = request.Id,
        Name = request.Name
    })
    .WithMap<Customer, CustomerResponse>(customer => new CustomerResponse
    {
        Id = customer.Id,
        Name = customer.Name
    })
    .WithValidRequest<CreateCustomerRequest>()
    .BuildAsync();

var handler = new CreateCustomerCommandHandler(host.Services);

var response = await handler.Handle(new CreateCustomerRequest(1, "Ada"));

Assert.Equal("Ada", response.Name);
Assert.True(host.Store<Customer>().Contains(customer => customer.Id == 1));
```

### Handler Integration Test

Use this when the test should exercise the same Pelican dispatch path as production.

Recommended characteristics:

- real DI
- real Pelican dispatch
- real TurtlePath handler base classes
- fake in-memory storage or SQLite

Example:

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .UsePelican(typeof(CreateCustomerCommandHandler).Assembly)
    .WithMap<CreateCustomerRequest, Customer>(request => new Customer
    {
        Id = request.Id,
        Name = request.Name
    })
    .WithMap<Customer, CustomerResponse>(customer => new CustomerResponse
    {
        Id = customer.Id,
        Name = customer.Name
    })
    .BuildAsync();

var response = await host.SendAsync(new CreateCustomerRequest(1, "Ada"));
```

### Automation Integration Test

Use this when the handler is generated by `TurtlePath.Automations`.

Automations should be tested through Pelican because the application does not own a concrete handler class.

Example:

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .UseAutomations(typeof(CustomerAutomationProfile).Assembly)
    .WithMap<CreateCustomerRequest, Customer>(request => new Customer
    {
        Id = request.Id,
        Name = request.Name
    })
    .WithMap<Customer, CustomerResponse>(customer => new CustomerResponse
    {
        Id = customer.Id,
        Name = customer.Name
    })
    .BuildAsync();

var response = await host.SendAsync(new CreateCustomerRequest(1, "Ada"));
```

## TurtlePathTestHostBuilder

`TurtlePathTestHost.Create()` returns a `TurtlePathTestHostBuilder`.

### UseTurtlePath

Registers the TurtlePath handler foundation.

```csharp
TurtlePathTestHost.Create()
    .UseTurtlePath(typeof(CustomerHooks).Assembly);
```

The test host registers TurtlePath by default. Use this method when you need to pass hook assemblies explicitly.

### UsePelican

Registers Pelican handlers from assemblies.

```csharp
TurtlePathTestHost.Create()
    .UsePelican(typeof(CreateCustomerCommandHandler).Assembly);
```

Use this when the test calls `host.SendAsync(...)` for manually written handlers.

### UseAutomations

Registers automation profiles and generated handlers.

```csharp
TurtlePathTestHost.Create()
    .UseAutomations(typeof(CustomerAutomationProfile).Assembly);
```

Use this when the flow is declared through `TurtlePath.Automations`.

### UseInMemoryStorage

Registers `InMemoryTurtlePathStorage` as both `IStorageReaderAdapter` and `IStorageWriterAdapter`.

This is enabled by default.

```csharp
TurtlePathTestHost.Create()
    .UseInMemoryStorage();
```

### WithoutInMemoryStorage

Disables in-memory storage registration.

This is useful when another package registers storage, such as `TurtlePath.Testing.EntityFrameworkCore`.

```csharp
TurtlePathTestHost.Create()
    .WithoutInMemoryStorage();
```

### ConfigureServices

Adds custom DI registrations.

```csharp
TurtlePathTestHost.Create()
    .ConfigureServices(services =>
    {
        services.AddSingleton<ICustomerRiskService, FakeCustomerRiskService>();
    });
```

Use this for feature services, custom hooks, custom steps, fake external services, or application-specific dependencies.

### WithMap

Registers a create/projection mapping delegate.

```csharp
TurtlePathTestHost.Create()
    .WithMap<CreateCustomerRequest, Customer>(request => new Customer
    {
        Id = request.Id,
        Name = request.Name
    });
```

Missing mappings fail with a clear exception. This is intentional: tests should say exactly how a request becomes an entity or response.

### WithUpdateMap

Registers a mapping delegate that updates an existing destination object.

```csharp
TurtlePathTestHost.Create()
    .WithUpdateMap<UpdateCustomerRequest, Customer>((request, customer) =>
    {
        customer.Name = request.Name;
        customer.Name = request.Name;
    });
```

Use this for update handlers and any flow that maps request values onto an existing entity.

### WithValidRequest

Marks a request type as valid.

```csharp
TurtlePathTestHost.Create()
    .WithValidRequest<CreateCustomerRequest>();
```

The delegate validator allows missing validators by default, but explicit `WithValidRequest<TRequest>()` makes test intent clearer.

### WithValidator

Registers custom validation behavior.

```csharp
TurtlePathTestHost.Create()
    .WithValidator<CreateCustomerRequest>((request, cancellationToken) =>
    {
        if (string.IsNullOrWhiteSpace(request.Name))
            throw new InvalidOperationException("Name is required.");

        return ValueTask.CompletedTask;
    });
```

Use this when the test needs to assert validation failure behavior without bringing a real validation provider.

### WithSeed

Seeds the in-memory storage.

```csharp
TurtlePathTestHost.Create()
    .WithSeed(
        new Customer { Id = 1, Name = "Ada" },
        new Customer { Id = 2, Name = "Grace" });
```

Seeded entities are available to query, update, delete, and assertion helpers.

### TraceHooks

Registers generic test hooks that capture command, response, and query hook stages.

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .TraceHooks()
    .BuildAsync();

var trace = host.Resolve<HookTrace>();

Assert.Contains(trace.Entries, entry => entry.Stage == "AfterSave");
```

Captured stages include:

- `BeforeValidation`
- `AfterValidation`
- `BeforeGetEntity`
- `AfterGetEntity`
- `BeforeMap`
- `AfterMap`
- `BeforePatch`
- `AfterPatch`
- `BeforeSave`
- `AfterSave`
- `BeforeDelete`
- `AfterDelete`
- `BeforeResponse`
- `AfterResponse`
- `BeforeQuery`
- `AfterQuery`

## TurtlePathTestHost

### Services

Gets the scoped service provider used by the test.

```csharp
var service = host.Services.GetRequiredService<ICustomerRiskService>();
```

### Resolve

Resolves a required service from the test scope.

```csharp
var handler = host.Resolve<CreateCustomerCommandHandler>();
```

### SendAsync

Dispatches Pelican requests.

```csharp
var response = await host.SendAsync(new CreateCustomerRequest(1, "Ada"));
```

Use this for handler integration tests and automation integration tests.

### Store

Gets assertion-friendly access to in-memory entities.

```csharp
Assert.True(host.Store<Customer>().Contains(customer => customer.Id == 1));
```

### Storage

Gets the in-memory storage instance.

```csharp
Assert.Contains(host.Storage.Operations, operation => operation.Action == "SaveChanges");
```

Recorded actions include:

- `Add`
- `Update`
- `Remove`
- `SaveChanges`

## In-Memory Storage

`InMemoryTurtlePathStorage` implements both:

- `IStorageReaderAdapter`
- `IStorageWriterAdapter`

It supports:

- add
- add range
- update operation tracing
- remove
- save operation tracing
- typed reads
- filters by expression
- sort by expression
- paging
- projection through `IMapperAdapter`

String filters and string sorts are intentionally no-op in the core testing package. Use `TurtlePath.Testing.Integration` with DataScorpio testing helpers, `TurtlePath.Testing.EntityFrameworkCore`, or a real filtering adapter when a test must prove provider-specific filter/sort behavior.

## Mapper Testing

`DelegateMapperAdapter` is explicit by design.

Register every mapping the tested flow needs:

```csharp
.WithMap<CreateCustomerRequest, Customer>(request => new Customer
{
    Id = request.Id,
    Name = request.Name
})
.WithMap<Customer, CustomerResponse>(customer => new CustomerResponse
{
    Id = customer.Id,
    Name = customer.Name
})
```

For update handlers:

```csharp
.WithUpdateMap<UpdateCustomerRequest, Customer>((request, customer) =>
{
    customer.Name = request.Name;
})
```

Use real OctoMap integration tests separately when the mapping profile itself is the thing being tested.

## Validator Testing

`DelegateValidatorAdapter` lets tests choose whether validation matters in the scenario.

For a happy path:

```csharp
.WithValidRequest<CreateCustomerRequest>()
```

For a validation failure:

```csharp
.WithValidator<CreateCustomerRequest>((request, cancellationToken) =>
{
    throw new InvalidOperationException("Invalid customer.");
})
```

Use real Crabalidator integration tests separately when the validator rules themselves are the thing being tested.

## Entity Framework Core Testing

Install `TurtlePath.Testing.EntityFrameworkCore` when the test should run against SQLite.

```xml
<PackageReference Include="TurtlePath.Testing.EntityFrameworkCore" Version="..." PrivateAssets="all" />
```

Register the DbContext:

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .UsePelican(typeof(CreateCustomerCommandHandler).Assembly)
    .UseSqliteDbContext<AppDbContext>(options => options with
    {
        ConfigurationAssemblies = [typeof(AppDbContext).Assembly]
    })
    .WithMap<CreateCustomerRequest, Customer>(request => new Customer
    {
        Id = request.Id,
        Name = request.Name
    })
    .WithMap<Customer, CustomerResponse>(customer => new CustomerResponse
    {
        Id = customer.Id,
        Name = customer.Name
    })
    .BuildAsync();

await host.CreateSchemaAsync<AppDbContext>();
```

Useful helpers:

- `UseSqliteDbContext<TDbContext>()`
- `CreateSchemaAsync<TDbContext>()`
- `ResetDatabaseAsync<TDbContext>()`
- `SeedAsync<TDbContext, TEntity>(...)`

Use SQLite tests for:

- EF entity configuration
- actual inserts/updates/deletes
- query translation
- CId conversion
- BaseDbContext conventions
- automation flows that need real persistence

## Exception Handling Testing

Use `UseExceptionHandling()` to register TurtlePath exception handling core.

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .UseExceptionHandling(builder =>
    {
        builder.For<InvalidOperationException>(
            ExceptionKind.Business,
            exception => exception.Message);
    })
    .BuildAsync();

var result = host.HandleException(new InvalidOperationException("Business failed."));

Assert.Equal(ExceptionKind.Business, result.Descriptor.Kind);
Assert.Equal("Business failed.", result.Descriptor.Messages.Single());
```

Use this for transport-neutral exception handling assertions. HTTP-specific response projection should be tested with the ASP.NET Core exception handling adapter.

## Jobs Testing

Use `UseJobs()` and `WithJob<TJob>()` for one-shot jobs.

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .UseExceptionHandling()
    .UseJobs()
    .WithJob<ImportCustomersJob>()
    .BuildAsync();

var result = await host.RunJobsAsync();

Assert.True(result.Succeeded);
```

The testing package registers logging for job tests so the worker exception handling services can resolve correctly.

Use job tests for:

- one-shot job execution
- retry behavior
- selected job execution
- failure behavior
- exception descriptor assertions

## Event Sourcing Testing

Install `TurtlePath.Testing.EventSourcing` when a test needs event stream assertions.

```xml
<PackageReference Include="TurtlePath.Testing.EventSourcing" Version="..." PrivateAssets="all" />
```

Read a stream:

```csharp
var events = await host.ReadEventStreamAsync("customers", customerId);

Assert.Contains(events, item => item.EventType == "customer-created");
```

Check for one event type:

```csharp
Assert.True(await host.StreamContainsEventAsync("customers", customerId, "customer-created"));
```

`EventSourcingTestEvent` exposes:

- `EventType`
- `StreamVersion`
- `Payload`
- `Metadata`

## Recommended Patterns

Use direct handler tests when:

- the handler is manually written
- the test focuses on handler behavior
- fake storage is enough
- mappings and validation can be represented by delegates

Use Pelican integration tests when:

- the request dispatch path matters
- handler registration matters
- pipeline behavior matters

Use automation integration tests when:

- the flow is declared through `TurtlePath.Automations`
- there is no concrete handler class in application code
- generated handler registration must be verified

Use SQLite integration tests when:

- EF configuration matters
- query translation matters
- CId conversion matters
- persistence behavior matters

Use adapter-specific tests when:

- OctoMap profile behavior is under test
- Crabalidator rules are under test
- DataScorpio filter/sort syntax is under test
- Event sourcing stream output is under test

## Integration Testing

Install `TurtlePath.Testing.Integration` when a test should compose the TurtlePath test host with testing adapters from the rest of the stack.

```xml
<PackageReference Include="TurtlePath.Testing.Integration" Version="..." PrivateAssets="all" />
```

Example:

```csharp
await using var host = await TurtlePathTestHost
    .Create()
    .UsePelicanTesting(typeof(CreateCustomerCommandHandler).Assembly)
    .UseOctoMapTesting(typeof(CustomerMappingProfile).Assembly)
    .UseCrabalidatorTesting(typeof(CreateCustomerRequestValidator).Assembly)
    .UsePigeonTesting(typeof(CustomersHubConsumer).Assembly)
    .UseSpiderTesting(typeof(TransactionBoundary).Assembly)
    .UseDynaBeeTesting()
    .UseKrackendTesting()
    .UseDataScorpioTesting(profiles => profiles.FromAssemblyOf<CustomerQueryProfile>())
    .BuildAsync();
```

The integration package only forwards registration to the owning testing packages. It does not duplicate their assertions, fakes, or traces.
